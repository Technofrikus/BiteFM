2 · APIClient is a shallow god-module

Strong

Sources/BiteFMCore/Networking/APIClient.swift — 1,325 lines, single @MainActor ObservableObject. Note: the favorite/played extraction (Candidate 1) reduced its *view-layer* surface but the module itself is unchanged — still mixes auth, live-metadata polling, favorites, history, archive, shows.

Solution

Split into focused sub-modules behind a thin facade: AuthModule, FavoritesModule (owns FavoriteStateLogic), HistoryModule, ArchiveModule, LiveMetadataModule, ShowsModule. APIClient becomes a facade owning the URLSession adapter and wiring. FavoritePlayedStore already shows the pattern to follow.

Benefits
  • Locality: favorite-toggle bugs live next to favorite state, not 800 lines from live-metadata polling.
  • Leverage: each sub-module is unit-testable with a stubbed URLSession — no SwiftUI or full object graph.
  • Tests: pure fetch/parse logic tested in isolation.
Before — one wide seam
Views ──observe──▶ APIClient (1,325 LOC)
  ├ auth · favorites · history
  ├ archive · liveMetadata · shows
any @Published → all views re-render
After — deep sub-modules
APIClient (facade + URLSession adapter)
  ├ AuthModule · FavoritesModule
  ├ HistoryModule · ArchiveModule
  └ LiveMetadataModule · ShowsModule
Views ──observe──▶ narrow store only

3 · Archive sectioning logic is duplicated and shallow

Worth exploring

ArchiveView.computeLetterSections / ArchiveNew.computeDaySections + ArchiveSectionHelpers.swift.

Problem

Two list views each implement their own Dictionary(grouping:) + locale sort + per-group sort, plus a private *SectionsSignature memo-cache. ArchiveSectionHelpers is a bag of three unrelated static functions — shallow by the deletion test. The grouping/sorting policy (A–Z rank, "#" first, de_DE collation) is split across two views with subtly different rules.

Solution

Extract a deep ArchiveSectioner module with two pure entry points: sectionByLetter(_ shows:) and sectionByDay(_ items:), each returning a value type that also encapsulates its own change-signature (so the memo-cache moves inside the module). ArchiveSectionHelpers is folded in or deleted.

Benefits
  • Locality: all collation rules in one module; a locale bug is fixed once.
  • Leverage: both archive tabs share one tested sectioner.
  • Tests: pure functions over [Show] / [StoredArchiveItem] — no SwiftUI, no @State cache logic.
Before
ArchiveView.computeLetterSections (group+sort+signature)
ArchiveNew.computeDaySections (group+sort+signature)
ArchiveSectionHelpers (3 loose statics)
After
ArchiveSectioner (deep module)
  ├ sectionByLetter(_:)
  └ sectionByDay(_:) // owns signature + cache
Views ──call──▶ result

4 · Live-metadata poll is coupled to the shared object

Worth exploring

APIClient.startLiveMetadataPolling / fetchLiveMetadata publishes liveMetadata on the shared object.

Problem

The 60s liveMetadata publish is the root cause of the re-render defenses. It lives on the shared APIClient, so its @Published is visible to all consumers whether they need it. Only LiveView and PlayerBarView (when live) consume it.

Solution

Move live-metadata into its own LiveMetadataStore (or the LiveMetadataModule from Candidate 2) that owns the polling task and republishes only to LiveView / PlayerBarView. APIClient stops publishing liveMetadata; the now-unnecessary re-render guards in list views can be removed as a follow-up.

Benefits
  • Locality: live-metadata lifecycle lives with its only consumers.
  • Leverage: removes the entire class of "ignore unrelated publish" code across list views.
  • Tests: the decode + equality-guard is unit-testable in isolation.
Before
APIClient.liveMetadata @Published (60s)
  └▶ ALL consumers re-evaluate
    list views add guards to ignore it
After
LiveMetadataStore (owns poll)
  └▶ LiveView, PlayerBarView (live only)
list views: no guard needed

Recommended next step

Candidate 2 (split APIClient) is the highest-leverage remaining work and now has a proven template — FavoritePlayedStore and ActivePlaybackStore show exactly how to carve a narrow store out of the shared object. Start with LiveMetadataModule (Candidate 4) as the first slice: it is the smallest, most isolated seam and directly removes the last re-render-defense code. Then proceed to FavoritesModule / HistoryModule / ArchiveModule.
